## 📚 Chapter 02. Task별 실전 인퍼런스 마스터 - 섹션 2.1 Pipeline API (Facade Pattern)

### 🎬 도입 스토리

어느 날 오후, 기획팀에서 급하게 요청이 들어왔습니다. "우리 서비스에 올라오는 사용자 리뷰가 긍정적인지 부정적인지 실시간으로 판단해서 대시보드에 뿌려줘야 해요. 당장 내일 아침 데모인데 가능할까요?"

여러분은 방금 배운 `AutoModel`과 `AutoTokenizer`를 떠올립니다. 모델을 고르고, 토크나이저를 세팅하고, 텐서를 만들고, 모델에 넣고, 나온 숫자(Logits)를 다시 확률값으로 변환(Softmax)하는 코드를 짜기 시작합니다. 그런데 생각보다 손이 많이 갑니다. "아, 이 과정을 누가 하나로 묶어놓지 않았을까?"

이때 시니어 개발자가 나타나 슬쩍 코드 한 줄을 보여줍니다. `classifier = pipeline("sentiment-analysis")`. 단 한 줄로 여러분이 고민하던 전처리, 추론, 후처리가 모두 끝납니다. 이것이 바로 **Pipeline API**입니다.

시니어는 단순히 "편하니까 써라"고 하지 않습니다. 이 뒤에 숨겨진 **Facade Pattern(퍼사드 패턴)** 의 미학을 이해하고, 언제 이 편의성을 취하고 언제 로우 레벨로 내려가야 할지를 판단하는 기준을 제시합니다.

>[!note]
> 퍼서드 패턴 <br>
> '퍼사드(Facade)'는 건축물의 '정면'을 뜻합니다. 소프트웨어 공학에서의 퍼사드 패턴은 **"복잡한 서브시스템들에 대해 단순화된 인터페이스를 제공하는 상위 수준의 인터페이스"** 를 정의합니다.<br>
> 복잡한 내부 구조를 감추고, 사용자가 핵심 기능에만 집중할 수 있도록 돕는 디자인 패턴입니다.

---

### Pipeline API란?
`pipeline`은 허깅페이스 `transformers` 라이브러리에서 가장 높은 수준의 추상화 객체입니다. 텍스트, 이미지, 오디오 등 다양한 모달리티의 데이터를 입력받아 즉시 최종 결과물을 반환합니다. 내부적으로는 우리가 챕터 1에서 배운 모든 구성 요소가 유기적으로 연결되어 있습니다. <br>
Pipeline은 내부적으로 **"전처리 -> 모델 추론 -> 후처리"** 라는 3단계 파이프라인 아키텍처를 자동으로 관리합니다.

### 퍼사드 패턴 (Facade Pattern)

'퍼사드(Facade)'는 건축물의 '정면'을 뜻합니다. 소프트웨어 공학에서의 퍼사드 패턴은 **"복잡한 서브시스템들에 대해 단순화된 인터페이스를 제공하는 상위 수준의 인터페이스"** 를 정의합니다.

* **왜 필요한가?**: `transformers` 라이브러리는 수천 개의 모델 아키텍처를 지원하느라 내부 구조가 매우 복잡합니다. 일반 개발자가 이 내부의 복잡한 클래스 관계를 다 알 필요 없이, "감성 분석", "요약", "번역"이라는 목적(Task)에만 집중하게 해 줍니다.
  
* **컴포넌트의 결합**: `pipeline` 객체는 내부적으로 다음 세 가지를 캡슐화(Encapsulation)합니다.

1. **Tokenizer/Processor**: 입력 데이터(Text, Image)를 숫자로 변환.

2. **Model**: 핵심 연산 수행 (가중치 계산).

3. **Post-processor**: 모델의 출력값(Logits)을 인간이 이해할 수 있는 형태(Label, Score)로 가공.


### 인퍼런스의 3단계 (The Inference Pipeline)

우리가 `pipeline("text-classification")`을 실행하면 내부 메모리와 CPU/GPU에서는 다음과 같은 단계가 진행됩니다.

1. **Pre-processing (전처리)**:
입력된 원문 텍스트가 토크나이저를 거쳐 `input_ids`와 `attention_mask` 텐서로 변환됩니다. 이때 패딩과 잘라내기가 자동으로 수행됩니다.

1. **Inference (추론)**:
생성된 텐서가 모델의 레이어들을 통과합니다. 이 과정에서 행렬 곱셈()이 수없이 반복되며 최종 레이어에서 **Logits**라 불리는 가공되지 않은 점수들이 나옵니다.

1. **Post-processing (후처리)**:
모델이 뱉은 Logits는 확률값이 아닙니다. 이를 확률로 바꾸기 위해 소프트맥스(Softmax) 함수를 적용합니다.

이후 가장 높은 확률을 가진 인덱스를 찾고(Argmax), 이를 모델 카드에 정의된 라벨(예: 'POSITIVE')과 매핑하여 반환합니다.

### 주의사항 및 베스트 프랙티스

* **유연성 vs 편의성**: `pipeline`은 매우 편하지만, 모델 내부의 특정 레이어에 접근하거나 복잡한 디코딩 전략을 세밀하게 제어하기에는 한계가 있습니다. 커스텀 로직이 많이 들어간다면 챕터 1에서 배운 로우 레벨 방식을 섞어 써야 합니다.

* **장치 할당(Device)**: 기본적으로 `pipeline`은 CPU에서 동작합니다. GPU를 쓰려면 `device=0` (첫 번째 GPU) 옵션을 명시해야 합니다. 시니어는 성능을 위해 항상 현재 실행 환경의 GPU 유무를 체크하는 코드를 함께 작성합니다.

* **배치 처리(Batching)**: 대량의 데이터를 처리할 때는 리스트 형태로 데이터를 넘겨주어 `pipeline` 내부의 최적화된 루프를 타게 하는 것이 속도 면에서 유리합니다.

### 🎓 핵심 요약

**이번 섹션에서 배운 것:**

1. **Pipeline API** - 전처리, 모델 추론, 후처리를 하나의 객체로 묶어 제공하는 고수준 인터페이스입니다.
2. **Facade Pattern** - 복잡한 내부 서브시스템을 감추고 사용자에게 단순한 창구를 제공하는 설계 철학을 이해했습니다.
3. **인퍼런스 메커니즘** - 텍스트가 토큰이 되고, 모델의 수치 연산을 거쳐, 다시 소프트맥스를 통해 의미 있는 결과로 변환되는 전체 흐름을 파악했습니다.

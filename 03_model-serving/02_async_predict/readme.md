## 📚 Chapter 03. FastAPI를 활용한 AI 모델 서빙 - 섹션 3.2 비동기(Async) 추론 처리

### 🎬 도입 스토리

어느 날 팀장님이 서비스 모니터링 대시보드를 보며 소리칩니다. "아니, 지금 동시 접속자가 5명밖에 안 되는데 왜 응답 시간이 10초나 걸리는 거죠? 서버 사양은 충분하잖아요!"

여러분은 코드를 살펴봅니다. 분명 FastAPI를 썼고 `async def`도 잘 붙였습니다. 그런데 왜 사용자가 한 명만 들어와도 다른 사용자들이 줄을 서서 기다려야 할까요?

범인은 바로 **'이벤트 루프 차단(Blocking the Event Loop)'** 입니다.

우리가 사용하는 AI 모델의 추론(Inference) 과정은 수천만 번의 행렬 곱셈을 수행하는 매우 무거운 **CPU/GPU 집약적(Compute-bound)** 작업입니다. 파이썬의 비동기 엔진인 이벤트 루프는 매우 효율적인 '주문 받는 직원'이지만, 이 직원이 직접 주방에 들어가서 10초 동안 요리(추론)를 시작하는 순간, 카운터에는 아무도 남지 않게 됩니다. 뒤에 선 손님들은 주문조차 하지 못한 채 서버가 죽었다고 생각하게 되죠.

오늘 우리는 시니어 개발자로서 이 '주문 받는 직원'과 '요리사'의 역할을 명확히 분리하고, 서버가 멈추지 않고 수많은 요청을 동시에 처리하게 만드는 **비동기 동시성 제어**의 정수를 배울 것입니다.

---

### I/O-bound vs CPU-bound
비동기 프로그래밍을 제대로 하려면 내가 다루는 작업의 성격을 먼저 파악해야 합니다.

* **I/O-bound (입출력 위주)**: 데이터베이스 쿼리, 외부 API 호출, 파일 읽기 등. CPU는 놀고 있고 응답이 오기를 기다리는 시간(Waiting)이 대부분인 작업입니다. `await`가 가장 빛을 발하는 순간입니다.
  
* **CPU-bound (연산 위주)**: AI 모델 추론, 이미지 처리, 대량의 데이터 계산 등. CPU나 GPU가 100% 가동되며 연산을 수행하는 작업입니다. **AI 서빙의 핵심은 바로 이 CPU-bound 작업을 어떻게 비동기 환경에서 관리하느냐에 있습니다.**


### 내부 동작 원리

**1. FastAPI의 이벤트 루프와 작업 스케줄링** <br>
FastAPI는 `asyncio` 기반의 이벤트 루프 위에서 돌아갑니다. 이벤트 루프는 단 하나의 스레드(Main Thread)에서 동작하며, `await`를 만날 때마다 `잠시 하던 일을 멈추고 다른 요청을 처리`합니다. <br>
하지만 모델 추론 코드인 `model(text)`는 `await`를 지원하지 않는 동기(Synchronous) 함수인 경우가 많습니다. 만약 `async def` 내부에서 이 동기 함수를 그대로 실행하면, 이벤트 루프 전체가 그 연산이 끝날 때까지 얼어붙습니다.

**2. 해결사: Thread Pool (스레드 풀)** <br>
이 문제를 해결하기 위해 FastAPI는 영리한 전략을 사용합니다.

* **`def` (일반 함수)**: 핸들러를 `async` 없이 정의하면, FastAPI는 이 함수를 별도의 'External Thread Pool'로 보내버립니다. 즉, 요리사에게 일을 시키고 직원은 다시 카운터로 돌아옵니다.
  
* **`async def` 내에서의 수동 처리**: 이미 `async def`로 작성했다면, 무거운 연산 부분만 `anyio.to_thread.run_sync`와 같은 도구를 사용해 스레드 풀로 넘겨야 합니다.

> [!note]
> External Thread Pool<br>
> External Thread Pool은 FastAPI가 내부적으로 관리하는 스레드 풀로, CPU-bound 작업을 격리하여 이벤트 루프의 멈춤 현상을 방지합니다. 이 스레드 풀은 기본적으로 시스템의 CPU 코어 수에 맞게 크기가 조정되며, 필요에 따라 커스터마이징할 수도 있습니다.

**3. OS 레벨: GIL(Global Interpreter Lock)의 영향** <br>
파이썬은 한 프로세스 내에서 동시에 하나의 바이트코드만 실행할 수 있도록 제한하는 `GIL`이 있습니다. <br>
"그럼 스레드 풀을 써도 결국 한 번에 하나만 연산되는 것 아닌가요?"라는 의문이 생길 수 있습니다.

* **통찰**: 다행히 PyTorch나 TensorFlow 같은 라이브러리의 핵심 연산은 C++ 수준에서 돌아가며, 이 과정에서 파이썬의 GIL을 해제(Release)합니다. 따라서 스레드 풀을 사용하면 여러 CPU 코어를 활용해 실제로 '어느 정도의' 병렬 처리가 가능해지며, 최소한 이벤트 루프가 멈추는 것은 완벽히 방지할 수 있습니다.

즉, 파이썬의 GIL은 OS 레벨에서 제한을 걸지만, AI 라이브러리들은 이 제한을 우회하여 멀티코어 활용이 가능하도록 설계되어 있습니다.

>[!note]
> GIL (Global Interpreter Lock) 돌아보기<br>
> GIL은 파이썬에서 **한 번에 하나의 스레드만 바이트코드를 실행할 수 있도록 하는 메커니즘**입니다. 이는 `메모리 관리의 단순화`와 `스레드 안전성 확보`를 위해 도입되었습니다. 파이썬은 메모리를 관리하기 위해 참조 카운팅(Reference Counting)을 사용하는데, 여러 스레드가 동시에 객체에 접근하여 참조 카운트를 변경하면 실제보다 숫자가 과도하게 증가하거나 감소할 수 있기 때문에 GIL을 통해 하나의 스레드만이 파이썬 객체에 접근하도록 보장합니다.
> 
> 그러나 GIL은 멀티스레딩의 성능을 제한하는 단점도 있습니다. 특히 CPU-bound 작업에서는 여러 스레드가 동시에 실행되지 못해 성능 저하가 발생할 수 있습니다. 다행히도, 많은 AI 라이브러리들은 C/C++로 작성된 핵심 연산에서 GIL을 해제하여 멀티코어 활용이 가능하도록 설계되어 있어 


### 주의사항 및 베스트 프랙티스

* **`async def` 안에서 `time.sleep()` 금지**: 이는 전체 서버를 멈추는 재앙입니다. 비동기 환경에서는 반드시 `await asyncio.sleep()`을 써야 합니다.
  
* **무거운 모델은 전용 프로세스로**: 만약 모델이 너무 무거워 스레드 풀로도 감당이 안 된다면(GIL의 영향이 크다면), `Celery`나 `Ray` 같은 별도의 작업 큐(Task Queue) 프로세스를 사용하는 것이 시니어의 아키텍처입니다. (이번 섹션에서는 스레드 풀 수준을 다룹니다.)

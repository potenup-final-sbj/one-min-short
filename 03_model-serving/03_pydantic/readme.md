## 📚 Chapter 03. FastAPI를 활용한 AI 모델 서빙 - 섹션 3.3 Pydantic을 이용한 입출력 규격화

### 🎬 도입 스토리

여러분, 아주 고급스러운 레스토랑의 지배인이 되었다고 상상해 봅시다. 우리 주방에는 세계 최고의 요리사(AI 모델)가 대기하고 있습니다. 그런데 손님들이 주문서에 "대충 맛있는 거", "0.5인분만", "저번에 먹었던 그거"라고 적어 보낸다면 어떨까요? 주방은 금방 마비될 것이고, 요리사는 스트레스로 인해 엉뚱한 요리(Runtime Error)를 내놓거나 아예 파업(Server Crash)을 선언할지도 모릅니다.

실무에서 AI API를 개발할 때 가장 빈번하게 발생하는 장애 중 하나가 바로 **'데이터 규격 불일치'** 입니다. 클라이언트는 숫자를 보내야 할 곳에 문자열을 보내고, 리스트를 기대한 곳에 단일 객체를 보냅니다. 주니어 개발자는 이를 방어하기 위해 함수 초입에 수십 줄의 `if-else`와 `isinstance()` 체크 코드를 작성하곤 합니다.

개발자는 이 문제를 **'데이터 계약(Data Contract)'** 의 관점에서 해결합니다. Pydantic이라는 강력한 도구를 사용하여, 데이터가 우리 주방(모델)에 들어오기 전에 엄격한 검문을 거치게 하고, 나가는 음식(응답) 또한 정해진 그릇에 예쁘게 담기도록 강제합니다. 오늘은 데이터의 무결성을 보장하는 현대적인 백엔드 설계의 정수를 배워보겠습니다.

> [!note]
> 데이터 계약(Data Contract)<br>
> 데이터 계약은 API의 입출력 데이터 형식과 제약 조건을 명확히 정의하는 것을 의미합니다. 이는 클라이언트와 서버 간의 상호작용에서 데이터 무결성을 보장하고, 런타임 오류를 예방하는 데 중요한 역할을 합니다.

---

### Pydantic과 데이터 무결성

Pydantic은 파이썬의 **Type Hinting**을 극대화하여 데이터 검증과 직렬화(Serialization)를 처리하는 라이브러리입니다. FastAPI와는 샴쌍둥이처럼 결합되어 있습니다.

* **검증(Validation)**: 들어온 데이터가 우리가 정의한 타입과 일치하는지 확인합니다.
  
* **강제(Coercion)**: "1"이라는 문자열이 들어왔을 때, 우리가 `int`로 정의했다면 자동으로 숫자 `1`로 변환해 줍니다.

* **직렬화(Serialization)**: 파이썬 객체를 JSON 형태의 문자열로, 혹은 그 반대로 변환하는 과정을 표준화합니다.

###  내부 동작 원리

**A. 메모리와 성능: 왜 Pydantic인가?** <br>
Pydantic V2는 핵심 로직이 **Rust**로 작성되었습니다.

* **실행 흐름**: 데이터가 네트워크를 타고 들어오면(JSON 바이트 스트림), 파이썬 인터프리터가 이를 처리하기 전에 Rust로 작성된 검증 엔진이 메모리 상에서 데이터를 훑습니다.

* **효율성**: 파이썬의 동적 타입 체크는 런타임에 상당한 오버헤드를 발생시키지만, Pydantic은 컴파일 레벨의 엄격함을 파이썬에 주입합니다. 이를 통해 수천 개의 필드를 가진 복잡한 JSON도 밀리초 단위로 검증할 수 있습니다.

> [!note]
> 컴파일 레벨 검증<br>
> Python은 컴파일 언어가 아니지만, Pydantic을 사용하여 데이터를 정의하면 해당 객체는 Rust의 객체를 검사하는 로직이 기계어로 미리 준비됩니다. 이후 해당 객체의 데이터가 주입되면 컴파일된 데이터의 타입을 한 번에 검증하게 되는데 인터프리터 방식과 같이 한 줄씩 처리하지 않기 때문에 훨씩 효율적입니다. <br>

**B. 데이터 계약(Data Contract)과 직렬화 오버헤드** <br>
네트워크 통신은 기본적으로 **텍스트(JSON)** 로 이루어지지만, 우리 모델은 **메모리 주소와 텐서**를 다룹니다.

* **Serialization Cost**: JSON 문자열을 파이썬 딕셔너리로 바꾸고, 다시 Pydantic 모델 인스턴스로 만드는 과정에는 메모리 할당이 수반됩니다.
  
* **관점**: 무분별하게 큰 JSON을 받는 것은 서버 메모리 파편화를 유발합니다. 따라서 Pydantic 모델에 `max_length`나 `Field` 제약 조건을 설정하여, OS가 감당할 수 있는 범위 내에서 데이터가 흘러가도록 제어해야 합니다.


**C. 자동 문서화(Swagger UI)의 원리** <Br>
FastAPI는 Pydantic 모델을 해석하여 **JSON Schema(ISO 표준)** 를 생성합니다. 이 스키마는 곧바로 `/docs` 경로의 Swagger UI로 변환됩니다. 이는 "우리 API는 이런 형식만 받는다"는 계약서를 전 세계 개발자에게 자동으로 배포하는 것과 같습니다.

### 주의사항 및 베스트 프랙티스

* **입력(Request)과 출력(Response)의 분리**: 입력받는 데이터 형식과 사용자에게 보여줄 데이터 형식은 달라야 합니다. 보안상 모델의 내부 점수나 민감 정보는 빼고 결과만 보여줘야 하기 때문입니다.
  
* **Optional의 함정**: `Optional[str] = None`과 같은 설정은 신중해야 합니다. AI 모델이 반드시 필요로 하는 값이 빠진 채 들어오면 내부에서 `NoneType` 에러가 발생합니다. 필수 값은 과감히 필수(Required)로 설정하세요.

* **Alias 사용**: 클라이언트는 `user_id` 대신 `userId`라는 카멜 케이스(CamelCase)를 쓸 수 있습니다. Pydantic의 `alias` 기능을 쓰면 내부 코드는 파이썬답게(Snake Case) 유지하면서 외부와는 유연하게 소통할 수 있습니다.

### 🎓 핵심 요약

**이번 섹션에서 배운 것:**

1. **Pydantic BaseModel** - 데이터 타입 힌트를 기반으로 자동 검증과 변환을 수행하는 데이터 계약의 핵심 도구입니다.
2. **Schema Enforcement** - `Field`와 `validator`를 사용하여 실무에서 발생할 수 있는 데이터 오염을 런타임 이전에 차단하는 법을 익혔습니다.
3. **Serialization 최적화** - JSON과 파이썬 객체 사이의 변환 과정을 규격화하여 유지보수성을 높이고 자동 문서화를 달성했습니다.

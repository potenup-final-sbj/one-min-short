## 📚 Chapter 03. FastAPI를 활용한 AI 모델 서빙 - 섹션 3.1 FastAPI와 모델 로딩 전략

### 🎬 도입 스토리

여러분은 이제 막 '실시간 욕설 필터링 서비스'의 백엔드 개발을 맡았습니다. 의욕이 넘치는 주니어 시절의 저는 아마 이런 코드를 짰을 겁니다. 사용자가 댓글을 달 때마다 호출되는 API 함수 안에 모델 로드 코드를 넣는 것이죠.

```python
@app.post("/predict")
def predict(text: str):
    model = AutoModel.from_pretrained("my-huge-model") # ❌ 매 요청마다 수 GB를 로드?
    return model(text)

```

이 코드를 배포하면 어떤 일이 벌어질까요?

1. 첫 번째 사용자가 접속합니다. 모델 로딩에 30초가 걸립니다. 사용자는 창을 닫아버립니다.
2. 두 번째 사용자가 접속합니다. 또 30초가 걸립니다.
3. 동시에 10명이 접속하면? 서버는 수십 GB의 메모리를 한꺼번에 점유하려다 'Out of Memory(OOM)' 에러와 함께 폭발하고 맙니다.

팀장님이 달려와 묻습니다. "왜 서버가 죽었죠? 모델을 메모리에 **단 한 번만** 올려둘 순 없나요?"

오늘 우리는 FastAPI의 **Lifespan Events**를 통해 모델을 서버 시작 시 딱 한 번 로드하고, 모든 요청이 이 자원을 공유하게 만드는 시니어의 서빙 전략을 배울 것입니다.

> [!note]
> 💡 **Lifespan Events란?** <br>
> FastAPI 애플리케이션의 시작과 종료 시점에 실행되는 특별한 이벤트 훅입니다. <br> 이를 활용해 서버가 시작될 때 무거운 AI 모델을 메모리에 로드하고, 종료 시점에 자원을 해제할 수 있습니다.

---

### 가용성(Availability)과 모델 상주

웹 서버에서 AI 모델은 '무거운 손님'입니다. 한 번 모시는 데 비용(시간, 메모리)이 많이 들지만, 한 번 모셔두면 다음부터는 매우 빠르게 일을 시킬 수 있습니다. 이를 **'모델을 메모리에 상주시킨다(Resident)'** 라고 표현합니다.

* **Cold Start**: 모델이 메모리에 없는 상태에서 로드하며 시작하는 첫 응답. (매우 느림)
* **Warm Start**: 이미 메모리에 로드된 모델을 사용하여 즉시 추론을 수행하는 상태. (매우 빠름)

### 내부 동작 원리

**1. FastAPI Lifespan의 메커니즘** <br>
과거에는 `on_event("startup")`을 썼지만, 현대적인 FastAPI는 `contextmanager` 기반의 **Lifespan**을 권장합니다. 


* **실행 흐름**:
1. `uvicorn` 실행 → 2. `lifespan` 진입 → 3. **모델 로딩(Blocking)** → 4. `yield` (여기서부터 API 요청 수신 시작) → 5. 서버 종료 신호 → 6. `yield` 이후 코드(자원 해제) 실행 → 7. 프로세스 종료.


* **왜 yield인가?**: `yield`를 기준으로 서버의 '생애 주기'를 나눕니다. `yield` 이전은 준비 기간, 이후는 정리 기간입니다. 준비가 끝나기 전까지 FastAPI는 외부 요청을 받지 않습니다. 즉, **"완벽하게 준비된 상태에서만 장사를 시작하겠다"** 는 선언입니다.

> [!note]
> `on_event` vs `Lifespan` <br>
> 과거 `on_event`를 사용하는 경우에는 다음과 같은 흐름을 갖게 됩니다. <br>
> 1. `on_event("startup")` : 서버가 실행되기 위해 준비하는 단계로 주로 모델 로딩과 같은 초기화 작업을 수행합니다. <br>
> 2. 서버 실행 : 모든 준비가 완료되면 서버는 클라이언트 요청을 처리하기 시작합니다. <br>
> 3. `on_event("shutdown")` : 서버가 종료될 때 호출되며, 자원 해제 및 정리 작업을 수행합니다. <br>
> 이러한 흐름에서 문제는 `on_event("startup")`와 `on_event("shutdown")` 사이에 시점이 달라서 관리가 어려울 수 있다는 점입니다. <br>
> 
> `Lifespan`은 `on_event`의 기능을 통합하여, 서버의 시작과 종료를 하나의 컨텍스트 매니저로 관리할 수 있게 해줍니다. 이로 인해 코드의 가독성과 유지보수성이 향상됩니다.

**2. 메모리 관점: 프로세스와 모델 공유** <br>
파이썬 웹 서버를 띄울 때 보통 여러 개의 **Worker(프로세스)** 를 띄웁니다.

* **주의사항** : 각 Worker는 독립된 메모리 공간을 가집니다. 만약 Worker가 4개이고 모델이 4GB라면, 총 16GB의 RAM이 필요합니다. 시니어는 이를 고려하여 Worker 수와 서버 사양을 매칭합니다. <br>(공유 메모리 기술이 있지만, 딥러닝 모델에서는 각 프로세스에 올리는 것이 일반적이고 안정적입니다.)

> [!note]
> **Worker(프로세스)** <br>
> FastAPI는 기본적으로 `uvicorn`과 같은 ASGI 서버 위에서 동작합니다. <br>
> `uvicorn`은 여러 개의 Worker 프로세스를 띄워 병렬로 요청을 처리할 수 있습니다. <br>각 Worker는 독립적인 메모리 공간을 가지며, 이는 다중 코어 CPU를 활용하여 성능을 향상시키는 데 도움이 됩니다. <br>
> 즉, 하나의 서버 인스턴스가 여러 개의 프로세스로 나뉘어 각기 다른 요청을 동시에 처리한다는 것으로 만약 `workers=4`로 설정하면, 4개의 독립된 프로세스가 생성되어 각각의 요청을 병렬로 처리한 다는 의미입니다.

**3. OS 레벨: 파일 디스크립터와 핸들** <br>
모델을 로드하는 것은 디스크의 수많은 가중치 파일을 열어 RAM 주소 공간에 매핑하는 과정입니다. <br> Lifespan에서 로드된 모델 객체는 프로세스가 살아있는 동안 **힙(Heap) 메모리**에 유지되며, 모든 요청(Thread/Coroutine)은 이 객체의 메모리 주소를 참조하여 연산만 수행합니다.

### 주의사항 및 베스트 프랙티스

* **전역 변수의 위험성**: 모델을 단순히 파일 최상단에 전역 변수로 선언하면 테스트 코드를 짤 때나 서버 설정이 바뀔 때 통제하기 어렵습니다. 반드시 FastAPI의 `app.state`에 저장하여 관리하세요.

* **Health Check**: 모델이 로드되는 동안 서버는 응답할 수 없습니다. 로드 완료 여부를 체크할 수 있는 `/health` 엔드포인트를 만드는 것이 운영의 기본입니다.

### 🎓 핵심 요약

**이번 섹션에서 배운 것:**

1. **Lifespan Events** - 서버의 시작과 끝을 관리하며, 무거운 AI 모델을 메모리에 한 번만 로드하는 전략의 핵심 도구입니다.
2. **App State** - FastAPI 인스턴스 내부에 모델 객체를 상주시켜 모든 요청이 자원을 안전하게 공유하는 법을 배웠습니다.
3. **Cold Start 방지** - 매 요청마다 모델을 로드하는 실수를 방지하고, 가용성을 높이는 설계를 이해했습니다.
